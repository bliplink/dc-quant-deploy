# OpenTradingCore 模拟公开版发布验收

本次验收针对 2026 年 11 月 26 日在 Mac mini 上重装的 T554 模拟系统。当前结论为 **暂缓整体发布**。候选源码位于 [GitHub 发布分支](https://github.com/bliplink/dc-quant-deploy/tree/release/public-simulation-20261126)。现役环境为 Apple Silicon、Colima、8 个虚拟 CPU、约 16 GiB 内存。四个 Order/Trade 节点和两个见证进程运行在同一台机器。单机故障会使整套服务中断。

## 性能口径

本轮 1,425 个配对样本反映 Robot 请求进入到 Order 发布的耗时。P50 为 25.947 ms，P95 为 44.805 ms，P99 为 68.924 ms。该窗口约每秒 4.75 笔成交。客户公网下单到收到最终成交回报的耗时应单独测量。

此前严格模式在 4 租户、16 个订单簿、每秒发送 1,000 笔的窗口中，每秒完成 61.90 笔最终成交，最终回执 P99 为 11.40 秒。生产性能门槛为持续每秒完成 1,000 笔且端到端 P99 不超过 20 ms。本版本严格、异步模式均缺少达标报告。

## 代码、构建和安装

部署仓库的 release/public-simulation-20261126 分支将已核验来源的组件放在 sources/ 下。Git 子模块记录精确提交。Admin 的开户与公开统计来自两个补丁来源，保留两者用于整合。交易网页对应 3816c16，Common 对应 b6dfdd7，运行 JAR 的 SHA-256 为 08887e899c04eb2481761b373ec4403f621616f1214c8ecd473d2991082eff8c。

网页构建脚本从锁定提交提取干净源码，调用组件自己的 Dockerfile，生成 linux/amd64、linux/arm64 的 OCI 镜像归档，并校验平台与源码版本。API 文档通过仓库自己的脚本准备公开内容。以下命令供构建机使用，需要 Git、Bash、Python 3 及支持多架构 OCI 导出的 Docker Buildx。

```bash
git submodule update --init -- sources/trade-web sources/public-web sources/api-docs sources/tenant-web sources/platform-web
./scripts/build-public-simulation-web.sh ./dist-images
```

完整服务器安装还需要可分发的应用镜像、部署配置及安装时生成的密钥。当前 Mac 重装流程依赖本机历史模板、旧控制目录和已归档的故障证据。新服务器上应生成单独的运行身份和双节点签名，执行真实首次安装与恢复验证。当前仓库的通用 install-saas.sh 尚未通过这套 T554 验收。

## 整体发布标准

1. 普通用户从主站选择租户、注册、入金、开多开空、平仓、撤单、提现，浏览器内即时可见，账户与账本逐笔一致。覆盖 PC、手机、公开行情及签名 API。
2. 在连续 Robot 报价成交时分别停止 Order/Trade A、B，核验旧主隔离、物理落盘确认、接管、追平、自动回主和完整业务对账。单副本及异步风险按已商定的回执合同验收。
3. 验证签名镜像、WAL 归档和回收，观察至少一个实际回收周期，验证回收后仍可重启、追平。发布说明列出观测时长和磁盘增长量。
4. 出具两种确认模式的下撤单、最终成交压测，分别列出发送量、受理量、最终成交量、拒绝量、积压、P99，以及资源瓶颈。
5. 用同一个发布标签在目标平台完成全新安装、重复运行、备份恢复和版本回退。公开发布清单列出镜像仓库、平台摘要、源码提交和验收记录。

## 复现定位与候选修复

条件单失败时的 Order 异常栈从 armConditionalOrder 进入旧的 mutationGuard，随后 requireStagedBeforeMutation 在真正提交之前拒绝了请求。Order 修复 78b2cce 让已经准备好提交的条件单使用分区锁，继续由 Common 验证并写入 WAL 后才公布订单。旧写法的拒绝检查继续生效。使用本次部署的 Common 和共享包编译后，只有 OrderFacade.class 改变。Order Maven 报告 252 项，其中 250 项通过、2 项跳过。部署仓库另有 40 项 Mac 回归测试通过。

20 项来源已锁定在 sources/ 中，含 19 个不同的代码仓库。清算服务的 53 个运行类与对应构建逐个一致。平台和租户门户已锁定候选源码，仍需比对运行页面和双语手册。公开主站的双架构构建包已通过 OCI 校验。交易 Web 的两个架构使用同一组已复核的静态资源，分别启动其中的 Nginx 可执行文件并核对首页摘要。在 Apple Silicon 上的 x86_64 测试使用指令仿真。

## 11 月 26 日晚间滚动替换与候选构建

Order A、B 已在原卷依次更换为 78b2cce，两侧的 Common 摘要保持一致。A 返回时第一次观测超时，继续观测同一进程后核对了 256 个分区的主备水位、WAL 和快照。B 停止后，A 用 107.232 秒完成全部分区单节点接管。B 回来后 380.230 秒恢复全部分区严格主备，演练记录包含单节点接管期间和回主期间的 Robot 业务。物理运行时复验通过。

原网页新注册账户在两轮滚动替换后已成功提交并撤销 8 种条件单配置，涵盖触发限价、市价、止损、止盈及百分比和绝对距离两种追踪止损。随后同一租户的市价开空返回 99（无可执行流动性）。测试账户的限价单曾出现在委托列表中，该列表不能证明当时已进入撮合簿。这个场景及双方的成交展示仍待核验。切换后的五分钟内 9 个租户产生了可关联成交，第 10 个租户 XS3YAL 的 Robot 报告订单分区拒绝写入。

GitHub Actions 在每次推送发布分支后，从对应提交构建候选镜像。5 个网页任务覆盖主站、交易页、租户门户、平台门户和 API 文档；交易核心任务覆盖 Order、Trade 和 MD，并比较实际打包的 Common 与共享库。每个镜像核对两个平台、源码版本和镜像层内容。工作流仅具有读取权限。构建摘要写入任务记录；未验收候选只在构建机临时保存。首轮网页任务均已完成，后端任务发现 Trade 的 Maven 默认依赖目录与其镜像配方不同，已统一指定输出路径。

在 [首次八项镜像全部通过的构建](https://github.com/bliplink/dc-quant-deploy/actions/runs/45848760234) 中，行情服务与 Order、Trade 所用的 Common 和共享包逐字节一致。仓库将后续候选用本机专用的 age 收件人公钥加密，再把密文和 SHA-256 清单保存到对应的 Actions 运行记录 3 天，供验收使用。私钥保存在发布机用户的受限目录，和交易签名密钥独立。下载后应先解密、逐项执行清单校验和 OCI 校验，再将相同归档交给业务验收。只有验收通过的同一份镜像才能提升为正式版本。公共镜像仓库及 Release 均未启用自动推送。

XS3YAL 的诊断随后确认，公开委托接口仍列出 76 笔旧 Robot 限价单，目标深度为买卖各 20 笔。使用该 Robot 账户的正常撤单接口，逐批移除切换前已记录的旧报价，并核对每笔的服务回执和委托列表；新提交的报价得到保留。Robot 随后自行补足 40 笔，恢复点价，10 个 Robot 均报告 RUNNING。这次有人工撤单干预，因此十租户全自动业务恢复验收仍待重跑。

市场单回归用例复现了另一个问题。内部 Robot 与客户委托在同一个报价簿上展示，双方有不同的交易隔离标记。旧实现只取最优一笔后检查标记，因此更优的内部报价可以遮住后面可执行的同类客户报价。修复使准入定价、撮合、跨多个报价的成交和挂单判断都遵循相同的隔离条件，保留自成交检查和 Common 落盘承诺。用同一用例分别加载修改前后的类，旧版返回“无可执行流动性”，新版选到真实客户报价。Order 全量 Maven 测试 252 项，250 通过，2 项跳过。

## 单个体验用户与租户做市账户成交（11 月 27 日候选）

公开模拟盘为每个租户配置独立做市账户。普通用户可向同一模拟结算域内的 Robot 买入或卖出，手续费、保证金、盈亏和持仓由 Trade 按账户结算。开启自动点价时另开一个模拟资金账户，和做市账户分别授权、分别入账。当前 Mac 的配置为每个新账户注入 10,000 模拟资金。页面显示挂单数不能证明顾客可以成交。

候选的 AdminSvr 和 RobotSvr 仅在模拟安装设置 `PUBLIC_SIMULATION_FUNDED_MAKERS=true` 时启用。新增试用租户使用开户流程生成专属交易凭证，并以固定业务流水号注资。开户服务核对租户、账户、结算域和金额，收回临时入金权限，最后启用报价。收到无法核验的入金结果时，任务进入对账状态。Robot 的对外模拟报价要求关闭外部对冲。订单和结算仍走现有 Order、Trade 和 Common。

现存租户按位置码逐个迁移。用 `python3 scripts/migrate-public-simulation-maker.py <Mac部署目录> <租户位置码>` 查看状态。两项服务已换成候选、模拟开关生效后，加 `--apply` 仅向该租户现有开户任务提交迁移。服务停用旧 Robot 并等它撤完委托、释放执行权，通过原账户分别向 Order 查询挂单，再记录旧账户和注资流水号、开设独立新账户。既有模拟资金和持仓仍归原账户。若显示 `NEEDS_RECONCILIATION`，用该租户的注资流水号核对 Trade 记账结果，再处理这个租户。

单用户验收使用 `tests/public-simulation-maker-browser.cjs`。设置 `SIMULATION_GENERATION`、`DEMO_LOCATION` 和私有的 `AUDIT_DIR`，必要时设置 `PLAYWRIGHT_ROOT`。脚本先核对运行代次和租户做市状态，再通过浏览器注册一名普通用户、模拟入金 100、执行市价开多、平多、开空、平空。每一步用两方订单号推导并比对双方成交编号，检查页面成交更新。最后核对多空持仓、冻结、保证金、手续费和已实现盈亏。运行会在该租户留下一个体验账户及四笔订单记录。

上线前，原 Mac 的 10 个 Robot 均在内部模拟域运行，每个报告 40 笔委托。下节记录它们在原环境中逐个迁移后的实测结果。

### 候选安装入口

安装器位于 `scripts/install-public-simulation.py`。它接受一个由当前账户独占的持久目录，首次安装要求 Docker 引擎没有容器和数据卷。它在该目录生成新的服务身份和 A/B 密钥。完成首次安装后，再次执行相同命令会核对现有服务、镜像和 512 个分区，保留现有数据库和签名。四个节点和应用核验完成后，安装器保存集群就绪记录，再通过开户接口申请十个模拟租户。它等待十个做市账户和点价账户完成模拟入金，十个 Robot 均有新心跳及在盘口的报价。开户过程中断后，再次执行会沿用原申请号及私有密码继续。集群尚未完成物理认证就中断时，安装器停止并保留现场。体验租户的申请资料仅存于安装代次目录内权限为 0600 的 `demo-tenant-applications.json`。

带到新机的离线包应包含 16 个 OCI 归档文件和 `simulation-images.json`。发布时另行提供该清单的 SHA256 和部署提交号。Linux 使用本地 Docker 引擎，macOS 的候选流程使用 Colima。安装机还需 Compose、Git、Python 3、OpenSSL 和 Skopeo。首次启动还需能获取数据库、ClickHouse 和 ZooKeeper 基础镜像。在对应部署提交下使用以下命令，变量分别指向实际交付的目录与校验值。

```sh
python3 scripts/install-public-simulation.py \
  --state-dir "$HOME/.opentradingcore/simulation" \
  --image-bundle "$RELEASE_IMAGE_DIRECTORY" \
  --bundle-sha256 "$RELEASE_MANIFEST_SHA256"
```

单机默认主站端口为 18094，交易页为 18088。主站的租户交易入口使用访问者当前的主机名。如果通过独立域名反向代理交易页，首次安装前可设置 `T554_TRADE_ORIGIN`，例如 `https://trade.example.com`。线上 DNS、证书和对外端口须与目标服务器部署对应。正式制品和校验值以通过整套验收的发布记录为准。

仅调整安装脚本时，在 Actions 手动运行候选工作流并填写 `candidate_run`，可以用上一轮已通过构建的原始加密镜像重做新机诊断。流程核对工作流身份、全部服务的构建结果及镜像构建输入；服务、依赖或 Common 门禁发生变化都需要重新构建。跨提交诊断只记录验证结果。正式交付包由完整成功的同一提交生成，导出命令为 `bash scripts/package-accepted-simulation.sh RUN_ID OWNER_IDENTITY OUTPUT_DIRECTORY`。解密身份仅由发布人保管，目标服务器接收 OCI 文件和已验收的校验清单。

全量 Linux 发布验收分别在原生 amd64 和 arm64 上启动同一批候选镜像。除逐租户市价开平仓外，浏览器还提交模拟出金并重发同一请求，核对余额只扣一次。首个租户另测限价挂单撤销、六种条件委托及两种跟踪止损回调方式。两个平台的完整作业均成功且归档清单一致后，发布人才能导出该批镜像。

### 使用完整交付目录

发布人从同一次双架构验收成功的运行导出交付目录。目录内的 `install.sh`、固定版本的 `deployment/`、16 个镜像归档及 `simulation-images.json` 应一起复制到新机。服务器无需登录 GitHub。确认 Docker、Compose、Python 3、Git、OpenSSL、Skopeo 可用后，从交付目录运行以下命令，把变量换成发布记录提供的校验值。

```sh
./install.sh "$RELEASE_MANIFEST_SHA256"
```

默认状态目录为 `~/.opentradingcore/simulation`，也可作为第二个参数传入。安装成功后在浏览器打开该机的 18094 端口，选择租户注册体验。重复执行同一命令会核验原代次和十个做市账户。首次安装需要能拉取基础镜像。

### 从 GitHub Actions 获取整套安装包

正式推送的 x86_64、ARM64 空盘安装与交易验收均通过后，工作流的最后一项作业核对两台主机的镜像清单，生成一个 `accepted-installer-<部署提交>` 制品，保留三天。交付人下载并解压该制品，核对任务摘要和 `SHA256SUMS`，在持有发布密钥的交付机执行以下命令。目标服务器只接收解包得到的 `simulation-release` 目录。

```sh
age -d -i "$OWNER_IDENTITY" -o simulation-release.tar simulation-release.tar.age
tar -xf simulation-release.tar
```

在新服务器的交付目录执行 `./install.sh <清单SHA256>`，参数取任务摘要中 `simulation-images.json` 对应的值。首次安装需要空 Docker 引擎及前文列出的依赖。
