# 混合交易覆盖连续性：隔离候选验收

日期：2026-09-29。Trade 本地提交 `d9342916ce8f6e88f83ddfe52ea02f26870d9eb1`。本轮解决候选层“普通交易推进 journal，但现金原结果索引覆盖不跟进”的问题；**不是所有线上普通交易已接入，也不是异常切主/TPS 验收**。

## 补齐内容与安全边界

新增显式、包内候选入口 `recordCoveredStateCandidate`，没有自动 bean 或现有 handler/recorder 接线。冻结已计算的已知 v1 非现金批次，检查效果版本、操作、租户/用户/产品/订单身份、重复效果与实际成交/lifecycle 去重键；v1 夹带现金原结果、旧现金来源/流水、未来效果或坏身份在追加前拒绝。候选要求明确非空交易 ID/source；它不是新的普通成交请求去重服务。

同一分区业务屏障内：严格 primary/epoch/READY、控制面和干净日志尾→上一段现金覆盖坐标完全相等且无本分区现金预留→状态及提交标记各有匹配的副本 ACK→精确 watermark transition→可信适配器安装并核对全部业务后态→推进覆盖→发布→再次复核权威/日志尾/watermark。覆盖推进不插入、删除、淘汰或重算任何现金原结果。

已知状态涵盖余额、持仓、账户/产品参数、订单像、成交去重和非现金不可变流水。这里是**协议与索引完整性检查，不是财务字段/业务计算/风险准入全量校验器**；未来真实适配器必须落实全部后态安装和核对，测试回调不能代表生产完成。旧 `record` 仍不推进候选覆盖：若夹入未观察的旧提交，不能直接补坐标跳过，须从可信本地文件恢复后再接续。

本分区现金预留阻止中性覆盖；其他分区预留仍占用现金容量但不挡中性区间。现金索引满时仍可推进中性覆盖、查询原结果，不允许淘汰原结果来接新现金。

追加开始后任何不确定 ACK、安装/核对失败、严重 Error、发布失败或 epoch/连接/READY/日志尾变化均封住分区、撤销 READY。已提交资金不回滚；恢复重放快照＋已提交 journal。安装/发布后的权威和尾坐标复核也补到原现金候选共享提交路径。脏尾不截断，不伪造基线或强制晋级。

## 下一步仍按底座优先

1. **全节点冷恢复/admission 容量门禁**：当前索引只核算已恢复记录与 pending，尚未恢复的其他分区不能被当成零占用；需要全节点可信预检/资源预留和失败后不开放新现金的验证。
2. 落实普通成交/配置/funding/保险/ADL 等全部真实适配器的后态、屏障与风险核对；旧资金 SQL writer 仍在，不启用双写。现金 API 认证身份/操作 ID/兼容、可信历史和财务对账继续保留门禁。
3. 冷请求/流水留存、推送遗漏/重复契约与 Projection GAP/重建收敛，不能靠本次原结果保存或对象重开代替。
