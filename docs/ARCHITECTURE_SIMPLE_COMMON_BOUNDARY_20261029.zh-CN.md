# OpenTradingCore｜简洁集群与代码职责边界（强制架构约束）

> **状态：必须遵循。** 适用于 `saas-crypto` 全部服务及后续新增服务。制定：2026-10-29。
> 本文优先于历史迭代计划中与之冲突的“业务专用集群”“复杂恢复事务”等方案。修改这条架构边界，必须事先取得项目负责人明确同意；不能因一次报错临时引入新的框架或协议。

## 开发优先级与验收门禁（最高优先级，禁止偏离）

**P0：只在 Demo+Common 开发、修复和完整验证集群底层。** Demo 是纯业务 `byte[]` 状态机；真正执行自动主备、WAL、TCP 复制、单节点降级、恢复追平、快照和归档的代码必须全部位于 Common。使用与将来 Order/Trade 相同的正式运行入口、常驻 Watch、相同 Common Jar 与持久化/恢复配置。不能把测试脚本主动执行主切、只进入 `RECOVERING`、容器 `Up` 或仅通过单测称为 HA 完成。

**P0 完成条件（全部必须有真实进程日志和水位证据）：** 真实 A/B 同时写入/备份 → SIGKILL A → B **自主接管、到 READY、继续接受业务写入** → A 自动重新加入并追平 → SIGKILL B → A 自主接管、到 READY、继续接受业务写入 → B 自动重新加入并追平；期间旧主隔离、无双主、已确认写入不丢失或重复、业务状态/快照/WAL 一致。备节点失联时可按明确声明的本地持久化级别继续写，但必须与严格双副本确认的保证区分。所有主备监测与恢复由 Common 常驻运行时自动执行，不通过脚本发命令冒充成功。

**P1：P0 验收通过后，Order/Trade 才能统一接入。** 必须复用 **同一版 Common Jar（SHA256 一致）、同一启动入口、同一自动 Watch/主切与恢复逻辑、同一 ACK/单节点降级语义**。只有业务状态机实现、分区数量、路径、成员/端口等必要配置可以不同。不得重新编写 Order/Trade 私有集群，也不得为订单类型、资金类别新增 Common 特殊分支；如果 Order/Trade 集群出现异常，先用原版 Demo+Common 复现与修复，不允许在两个业务服务分别打 HA 补丁。

**P2：P1 复用完成后才进行业务端到端验收。** 新租户自动审批、Robot 报价与 Tape 成交、Order/Trade 持久化及主备互切、成交/委托/资金/持仓、MD recentTrades 和 MySQL 投影全部核验一致。完整 P2 通过后才宣告 Demo 交付。

**禁止跳关、禁止并行发明第二套集群机制。** 若 P0 不通过，则 P1/P2 集群验收保持 STOP/NO-GO。参考 `docs/T266_DEMO_COMMON_ORDER_TRADE_PARITY_FIRST_20261029.zh-CN.md`。

## 一、唯一设计目标

**集群是通用的二进制数据存储与恢复机制，不是业务引擎。**

各业务进程自己决定生成、修改、校验什么数据，并将要持久化的状态变化编码为 `byte[]` 交给 Common。业务进程负责解码、应用、重放和生成 Snapshot。**Common 不理解字节里的任何字段。**

最常见部署是每个分区一个 Primary，向 Replica **单向 TCP 复制**；业务进程不因备节点短暂故障而被不相关节点拖死。后续扩容增加节点和分区即可，不能让每个节点无差别向全部节点广播复制。

## 二、代码放在哪里

| 所属模块 | 仅属于该模块的职责 |
|---|---|
| **Common** | 分区/节点路由与角色、主备授予和旧主隔离、通用 WAL 持久化和提交水位、TCP 单向复制、Snapshot、Diff/重放、归档清理、故障后自动恢复/切换 |
| **OrderSvr** | 所有订单类型和业务状态流转、OrderBook、订单校验与撮合、成交事件、自己的 `byte[]` 编解码及状态机 `apply/replay/snapshot` |
| **TradeSvr** | 余额、资金流水、持仓、杠杆设置、手续费、成交结算、风控、幂等、自己的 `byte[]` 编解码及状态机 `apply/replay/snapshot` |
| **MDSvr** | 行情订阅、盘口、成交和指标的业务构造；按通用 Snapshot/Diff 接口重建行情，不在 Common 中加入行情语义 |
| **Gateway** | 原业务消息透传，不因集群故障设计修改其传输语义 |

**禁止**在 Common 内加入 `Order`、`Position`、`Balance`、`TimeInForce`、`IOC/GTC/FOK/PO` 等业务字段、状态或分支；禁止让签名/复制/持久化层决定“哪些合法订单或资金类型可以存”。Order/Trade 业务层当然仍必须执行自身的合法性校验、撮合、资金检查、权限和去重。

## 三、保持最小化的通用接口与写入流程

逻辑上只有以下步骤，调用形式可适配现有 Common 代码，不因文档重新发明接口名称：

1. **业务进程**按自己的规则计算状态变化，将业务事件或状态编码为 `byte[]`。
2. **Common**按分区追加原始 `byte[]` 到 WAL，维护本地可恢复水位，并向指定备节点复制；不解析字节。
3. 达到所选持久化承诺后，**业务进程**应用对应状态变更并向调用方返回结果。不能在提交失败后对外声称成功。
4. **恢复时** Common 根据已确认提交水位恢复连续数据，忽略尚未确认的末尾记录；业务进程按相同顺序重放自己的 `byte[]` 状态。
5. 快照、日志归档、保留天数由 Common 通用管理，业务进程只提供自身 Snapshot/Apply 实现。

所有业务写操作走**同一个**通用存储入口。不能再增加“GTC 专用签名提交”“Filled 专用 Common WAL”“Balance 专用复制链路”或相互平行的第二套持久化机制。业务事件之间的先后关系或原子性由业务进程设计，Common 不设业务类型白名单。

## 四、恢复和 HA：够用就好

**不再设计新的恢复流程子系统**。继续使用现有 WAL、提交水位、Snapshot、复制及已有的最小节点授予/撤权机制，解决所有分区的一致性问题。

- 恢复关键判断：**已确认的提交记录可以恢复，未确认尾部不可以冒充已提交**。在写入前，Common 需要把本地可写数据位置与真实确认水位对齐，并在需要时从有效副本同步缺失的已提交记录。
- 旧 Primary 必须被隔离，不能双主；已确认的客户端 ACK 不得丢失或重复应用。**不能**因简化而直接放宽 WAL 哈希、提交边界或 Epoch 校验。
- 若无法确定哪个水位是真正已提交，应拒绝危险写入并报告原因，**不能伪造 ACK，也不能以脚本强行切换代替自动 HA**。
- **禁止再新增**恢复专用账本、恢复票据托管链、第二套 Custody/Receipt、业务类型特制恢复计划、层层 READY 门禁或需要人工执行的多步修复工作流；现有必要机制应精简和复用，而非叠加新机制。
- 单节点可继续工作是产品要求；备节点不可用时允许按清楚标记的**单节点持久化级别**运行。必须区分“本地已持久化”和“多节点已复制”，不能把未复制的数据说成具有跨机器零丢失保证。
- ZooKeeper 仅用于成员、角色和主切控制，**不能进入每笔业务写入热路径**；复制走 TCP，优先异步与低 CPU/IO，避免重复 fsync 或广播。

## 五、工程边界与验收

- 遇到启动或 WAL 错误，先定位**具体通用层的哪条条件**，不要不断添加业务白名单、认证模式、条件开关或恢复子流程。
- 修 Common 的共性问题，不让 Order/Trade 各实现一套主备；修业务自己的数据格式或状态机则只改对应业务服务。
- 以 Mac Demo 真实验收为主；必要时允许清空 **Demo** 数据重新注册租户，但**清空数据不等于 HA 恢复通过**。
- 最终必须验证：新租户自动审批 → Robot 自动报价 → Tape 真实成交 → Order/Trade A/B 自动互切 → 资金、持仓、订单与成交一致。单测/启动成功不是最终 PASS。
- 任何 PR/补丁如增加新持久化/恢复类、集群开关、额外 RPC/签名或业务数据分支，必须先说明为何**现有 Common 最小机制无法解决**，并遵守本约束；否则不得合入。
