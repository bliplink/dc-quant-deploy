# OpenTradingCore｜A/B 分区互备、自动接管与自动切回（统一强制架构）

> **生效日期：2026-10-31｜状态：架构目标已确认，在线 HA 与交易尚未通过。**
> 对涉及 A/B 放置、故障选主、恢复后是否回主、节点级/分区级恢复的历史设计，本文与 `ARCHITECTURE_SIMPLE_COMMON_BOUNDARY_20261029.zh-CN.md` 为最终依据。本文是**架构合同，不是实际部署通过的验收结果**。任何偏离需项目负责人明确确认。

## 一、唯一目标：平时各承担一半主分区，故障时完整接管，恢复后恢复原主

默认每个服务 **256 分区 / A、B 两个数据节点 / 每分区 RF=2**；独立服务有各自分区集与 WAL，不混用 Order、Trade 的业务内容。

| 分区 | Home Primary（固定归属） | 正常 Current Primary | 正常 Replica |
|---|---|---|---|
| P000–P127 | A | A | B |
| P128–P255 | B | B | A |

- A/B 平时分别 **128 主 + 128 备**，不存在“整节点只能是主”或“整节点只能是备”。每个分区任何时刻**最多 1 个 Current Primary**，仅向指定备份节点单向推送 WAL；返回的累计 fsync/ACK 是复制确认，不是反向复制或第二套选主。
- **A 故障**：Common 按分区确认 A 的旧写权限已失效、B 有资格接手对应已确认提交前缀，然后 B **自动**接管原属 A 的 128 个主分区；B 原有 128 个主分区不被打断。A 故障期间 B 处理 256 个主分区，需预留 CPU/内存/IO 能力。
- **A 恢复**：A 禁止直接恢复旧 Epoch 写入；先以 Learner/Replica 从 B 按 Snapshot + WAL 追平 **B 故障期间及恢复期间已确认的全部提交记录**，校验业务 State、去重水位、连续性和当前授权；随后 Common **自动发起归还原主分区的安全切换**，P000–P127 重新由 A 当主、B 当备。P128–P255 一直由 B 当主、A 当备。
- **B 故障**：对称执行，A 接管 P128–P255；B 返回先追平，再由 Common 自动把 P128–P255 切回 B 当主。
- **A 再挂 / B 再挂 / 互切往返**：以上机制无限重复，不能要求脚本逐个分区执行提升或恢复，不能要求人工签发 READY；允许受控有界暂停，不允许双主、重复成交或重复资金结算。
- 只对需要迁移的分区升 Epoch；**不是节点 A/B 角色整体对换**，不得影响另外的健康分区。已有在用分区不得重新执行初始化 Planner 来覆盖或删除历史。

## 二、只保留两项角色信息和最少控制状态

| 概念 | 作用 |
|---|---|
| `HomePrimary`（稳定、可恢复） | 初始化或经显式安全迁移确认的分区默认归属；故障切换不能修改它。不得从当前 Primary 推导 Home。 |
| `CurrentPrimary`（动态） | 本次持有合法写入权限的节点，由 ZooKeeper 控制面 CAS 与当前 Epoch 决定。 |
| `Epoch`（单调递增） | 每次实际授权迁移，包括恢复后的自动切回，都要递增，旧 Epoch 不得再次获得 ACK。 |
| `READY / RECOVERING` | 仅对外表现是否可授权路由；复杂内部持久化/恢复过程是 Common 的内部实现，不增加业务层选主状态机。 |

**默认分区归属是稳定配置/初始 Assignment 的持久事实**，不是独立于 Common 的第二套选主器。运行时恢复后按已经固定的 Home 目标做**一次普通分区级 Epoch 切换**；不新增“failback 选主算法”“业务特殊恢复协议”或每分区不断轮询 ZooKeeper。扩容/迁移时须通过正常的追平和 Epoch CAS 安全地改变 Home，绝不因节点排序变化暗中漂移。

## 三、故障与自动回切：同一个 Common 生命周期

1. **正常：** 一个分区 Primary 做业务 `byte[]` WAL/group fsync、按明示持久化合同 ACK；向唯一指定 Replica 用长期 TCP 流传输增量，备机按顺序落盘并反馈累计水位。ZK 仅低频记录成员、Epoch、租约与分区授权；不得进入每条交易的网络热路径。
2. **异常检测：** Common 发现节点 ZK 租约到期/失联、Primary WAL 已不可确定且真实撤权成立、或有效写权限失效。**仅阻止受影响分区的旧主**，健康分区继续写。节点还活着但某分区写入器失效时，不能等待整个节点的 ephemeral 租约消失，也不能仅凭另一个节点猜测它已失效。
3. **安全接管：** Common 要求可验证旧主隔离、候选 Replica 已覆盖所有可能已确认数据的可信提交水位，再通过**同一 ZooKeeper 原子 Epoch CAS**取得该分区新授权。没有条件不得 READY/ACK；不允许两个节点各自独立选主或由验收脚本手工改角色。
4. **B 单节点服务（如 A 挂）：** 必须保留明确的持久化模式。`QUORUM_DURABLE` RF2 严格 2/2 无第二真实数据副本时不能冒充成功；若按产品要求单节点继续报价/下单，必须明确、可核验地使用 `LOCAL_DURABLE_ASYNC` 或正式声明的自动降级合同，并在提交记录/ACK 中标明可能的复制滞后与 RPO 风险。ZooKeeper 投票节点不等于业务 WAL 副本。
5. **A 回归：** A 只能作为 Learner/Replica 接入，隔离不可信旧 WAL 尾部，接收现任 B 的合法 Snapshot + 增量 WAL，恢复业务 byte[] 状态及幂等索引。**任何未确认尾部不得重放为已提交订单或资金。**
6. **自动切回 Home：** A 的提交水位/状态与 B 一致、旧 Epoch 不能写且新副本关系和持久化合同满足后，Common 在 P000–P127 上逐分区/有界批量执行一次**正常角色转移**：冻结旧主该分区新提交 → 校验已确认水位与本地落盘 → CAS 新 Epoch / owner → 切换 CurrentPrimary 至 Home=A → B 成为 Replica → READY。重复触发应幂等，未完成则保持当前合法主，不反复震荡；不能在 A 刚重启、未追平时抢主。
7. **恢复正常：** 恢复 A/B 各 128 主、128 备；重新检查全部分区最终 Home 与 Current 一致及业务一致性。

上述流程必须由**现有唯一 Common runtime**承载；Home 回切是普通有证据的角色转移，不能为每一个 Order/Trade 添加特殊 Watch、Recovery Controller、二次恢复账本、人工控制脚本或新的公用外部微服务。

## 四、Common / Order / Trade / MD / Gateway 的代码边界

- **Common 独占：** 初始化归属/当前授权/Epoch/ZK CAS、常驻故障 Watch、旧写入器撤权、通用 WAL/提交水位、TCP 复制、Snapshot、恢复追平、Home 自动切回、日志归档、恢复后 READY。**Common 永远只看业务的 `byte[]`，不得按 GTC/IOC/FOK、订单、成交、余额或持仓分类。**
- **Order、Trade：** 提供自己的 `byte[]` 序列化、确定性 apply/replay、snapshot、业务合法性/幂等、订单/成交与账本一致性；调用**相同 Common 运行时接口**，不再保留各自复制、选主、恢复器或私有 READY。
- **MD：** 用通用 Snapshot/Diff/订阅框架恢复行情，行情业务语义由 MD 处理。
- **Gateway：** 按原有 ZooKeeper 服务发现和消息透传连接当前业务节点；不把业务选主算法下沉到 Gateway，也不要求 Gateway 修改已有消息内容。
- **性能：** 批量 WAL fsync / TCP 单向复制 / 累计 ACK，节点级批量 ZK 更新，禁止每个分区、每条业务请求同步访问 ZK、全历史重复 SHA 或重复签名；故障恢复证据不应堆成新的常态业务热路径。

## 五、必须保留的最小安全事实（不因简化移除）

- 每个可写分区只有一个被认证的 Epoch/Primary；旧节点的过期 Epoch 永久无效（包括 ZK 断网和物理写失败）。
- 已经对外 ACK 的订单、成交、余额、持仓变更，其确切提交前缀必须可追溯；不把未确认 WAL 尾部当成功。
- 严格数据副本持久化证明与 ZooKeeper 多数授权**不是同一件事**；仅 RF2 两数据节点且失去其中一个时，单机继续交易必须明确接受该期间本地持久写尚未复制的风险，不能同时声称严格零丢失。
- 恢复后的先追平、再授权、再路由；失败时保留最后一个**合法**状态，禁止伪造 RECOVERED/READY、伪造收据、无认证擦除旧证据。
- 不新增业务专用认证、专用 WAL 或资金/委托类型门禁；已有恢复内部状态尽可能收敛复用，不能只是把复杂度转移到 Order/Trade 或部署脚本。

## 六、唯一验收标准（实际 Docker/JVM 自动化，不是控制脚本替代切换）

| 步骤 | 自动行为及必须核对的证据 |
|---|---|
| T1 | 新部署 256 分区：A 主 128/备 128，B 主 128/备 128；独立服务、分区归属与 Replica 一致 |
| T2 | A/B 同时持续业务写，完整 WAL/ACK/业务状态与副本一致，记录分区路由和 Epoch |
| T3 | `SIGKILL A`：B 自主接管全部原 A 分区，继续已声明持久化合同的写入，无双主、无重复 |
| T4 | A 重启：自动作为 Learner/Replica 追平 B 新提交的 Snapshot+WAL，**不提前抢回 Primary** |
| T5 | A 追平后：**无需人工或脚本切主**，P000–P127 在新 Epoch 自动恢复 A 主、B 备；P128–P255 始终 B 主 |
| T6 | `SIGKILL B`：A 自主接管 B 原有主分区，确认旧 B Epoch 被隔离 |
| T7 | B 重启并追平：P128–P255 **自动切回 B 主**，全局恢复最初 128/128；反复双向故障注入 |
| T8 | 在整个切换期间核验已 ACK 提交水位、WAL 前缀、订单/成交/资金/持仓/Projection 一致性和 requestId 幂等；明确报告单节点降级期间的 RPO 风险和停顿时长 |
| T9 | Common Demo 验收后以相同 SHA256 Common Jar 部署 Order/Trade，注册新租户→自动审批→Robot 报价/Tape→真实部分成交、撤单、平仓→MD/K线/24h，故障前后不双算资金 |

**验收结果只能标注 `PASS`（自动化实测证据完整）或 `NO-GO`（任何步骤缺失）；启动成功、单元测试通过、脚本手工切换和仅 RECOVERING 均不算完成。**

## 七、立即执行的收敛顺序

1. **最高优先级**：以现有 Common Demo 唯一运行时完成分区级实际旧主撤权、自动新 Epoch 接管、单节点明示可写、回归后的自动 Home 切回。先修旧机制不一致，**禁止再增加并列选主路径**。
