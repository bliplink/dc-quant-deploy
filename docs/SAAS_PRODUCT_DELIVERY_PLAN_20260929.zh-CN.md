# DC SaaS 产品与工程交付计划

> 更新：2026-09-29。本文是当前执行计划；历史验收数字与旧路线图仍保留作证据，不自动代表当前版本通过。目标环境分为本地 Colima 验证、隔离验收环境、生产候选环境；未注明的通过结论不得跨环境继承。

> 最新执行优先级：用户要求先打好底座，近期主线为 **Order/Trade/MD 集群、受控压测、异常切换与稳定性**，同时开发可供后续服务按需接入的公共集群框架。具体顺序、已知恢复慢原因和框架边界见[可复用集群底座执行计划](REUSABLE_CLUSTER_FOUNDATION_PLAN_20260929.zh-CN.md)。这调整近期执行顺序，不撤销交易数据正确性和真实资金禁入门槛。

## 1. 产品目标与交付顺序

目标是把现有永续合约交易闭环发展为可供租户独立运营、最终能够承载真实资金的交易所核心，而不是只交付一个 Web 页面或单机撮合程序。交付顺序为：

1. 保证交易核心的业务与数据计算正确：订单撮合、成交、手续费、盈亏、保证金、资金费、强平、保险基金、ADL、余额与持仓必须符合规则，并在重启、重放、故障和长时间运行后保持一致。
2. 把 Broker API 和 Trade API 做成可独立使用的产品：租户只依赖 Broker API 能自建交易所；策略程序只依赖 Trade API 能运行 Robot。
3. 完成集群横向扩展、受控迁移、异常切换和故障域隔离；在真实混合流量下验证稳定性和容量。
4. 在核心、API 与集群基线稳定后，先完善租户管理，再完善平台管理。基础的 `location` 授权隔离不能等到 UI 完善阶段，必须贯穿前面每一步。
5. 账本、对账、生产价格、托管、安全合规和灾备门槛全部通过之前，不开放真实资金充值/提现。

Broker 与 Trade 使用同一套交易业务语义，不复制撮合实现。`type=trade` 只能操作 API Key 所属账户；`type=broker` 必须显式指定本租户客户，且服务端按会话中的权威 `location` 校验。Robot 是外部策略客户端，只通过公开 GW/API 访问交易能力，不以直连数据库或内部服务作为产品契约。

## 3. 工作流 A：交易核心正确性与恢复（先做）

### A1. 事故后的低风险验收

- 只读核对 Order/Trade 分区 assignment、epoch、Primary/Replica、READY 和路由；特别记录 P089/P019 状态，但不把它们当作唯一代表。
- 核对 Order/Trade committed tail、Replica ACK、snapshot、Projection watermark/GAP；抽样验证订单、成交、余额、持仓和手续费收敛。
- 核对 MySQL、ClickHouse、ZooKeeper 数据目录与服务健康。启动前要求数据盘已挂载，禁止容器在空 `/data` 上初始化新业务数据。
- 记录 Colima 事故备份与临时数据的保留位置、恢复过程和后续处置；本机副本不是异地备份。
- 上述检查通过后，再运行有明确数据隔离和清理门禁的端到端验收；不直接在脏压力账户上重复发单。

### A2. 业务计算与状态不变量

- 用独立于被测服务的预期结果/参考计算器核对价格时间优先、订单类型、部分成交、maker/taker、撤单竞态和自成交保护；不能只比较两个都可能出错的数据库投影。
- 对每笔成交复算成交额、手续费、已实现/未实现盈亏、保证金占用与释放、杠杆和风险档位；对资金费、部分/最终强平、破产价、保险基金及 ADL 建立有明确输入和预期输出的业务用例。
- 每轮业务操作后核对订单、双方执行记录、资金流水、余额、持仓、保证金和风险状态；不得出现无来源资金、重复扣款、负值穿透或未解释的差额。发现差异时保留事件与计算输入，门禁失败，不以“最终页面看起来正确”放行。
- 客户端已收到成功的订单/资金变更，故障后必须可恢复；未提交 tail 不得在切主后成为已确认状态。
- 任一分区同一 epoch 只允许一个可写 Primary；旧 epoch、旧 Primary、未 READY 的节点必须拒写。
- 重复请求、超时重试、消息重放、成交/撤单竞态不能造成重复成交或重复资金变动。
- Order/Trade journal 与 Projection 查询模型最终收敛，长期 GAP 或 watermark 停滞视为失败。
- 真实资金门槛另要求不可变复式账本、幂等资金事件、持续对账及极端行情/强平回放。账本不要求把 MySQL 放回同步撮合热路径，但必须能从持久事件证明每笔资金效果。

**完成证据：** 当前镜像的逐场景业务输入、独立预期计算、实际订单/执行/资金分录/余额/持仓差异报告，外加故障前后 committed prefix 对比、Projection 收敛报告和无双主证据；不能只提供进程存活截图。

## 4. 工作流 B：Broker API 与 Trade API 产品化

### B1. Broker API：只用 API 建一个交易所

- 覆盖租户客户创建/启停、`externalCustomerId` 幂等映射、账户配置、代客下撤单、订单/成交/余额/持仓/历史查询、行情与私有实时流、资金记录和审计。
- 保留 `owner=customer` 与 `actor=broker key/管理员` 两个身份；所有 `customerId` 操作逐次验证与 Broker 相同的 `location`，跨租户默认拒绝。
- 提供可运行的独立样板交易所（客户后台 + 简单交易前台），只用公开 API，不直连 MySQL、ZooKeeper、内部服务端口或容器文件。
- 测试充值/提现只用于模拟资金闭环。真实资金接口必须接入账本、钱包/托管、审批和对账后才开放。

### B2. Trade API：只用 API 写 Robot 策略

- `type=trade` Key 只交易自己的账户；支持行情/订单簿、下单/撤单/查单、余额/持仓、私有成交与订单回报。
- 固定 `clientOrderId` 幂等、请求超时后的查单判定、snapshot + sequence + GAP 检测、断线重订阅/补偿、限流和错误码；禁止把“超时”直接等同于“未成交”。
- 提供只连接公开 GW/API 的示例 Robot；网络断开、Robot/GW 重启和部分成交后能恢复敞口，不能重复下单或重复对冲。

### B3. 共同 API 发布门槛

- 以 `docs/openapi/` 的 Markdown 与机器可读契约为源，锁定 v1 字段、权限、错误、版本兼容及弃用策略；CI 做服务与文档的契约测试。
- API Key 分权、一次性交付 Secret、轮换/撤销、来源 IP 策略、签名/防重放、按 IP/Key/用户/`location` 分层限流与审计。
- 两个样板客户端在双租户环境完成交易、实时回报、故障恢复和越权测试，且不需要内部特权。高级 Binance/Bybit 兼容层可后续扩展，不阻挡基础 API 的独立可用性验收。

**完成证据：** 可重复运行的样板客户端、OpenAPI/Topic 契约测试、权限矩阵、断线/重试结果及双租户负例。

## 5. 工作流 C：集群扩展、异常切换与稳定性

- 先确定业务 SLO、每项关键服务的 RTO/RPO 与可接受的故障降级方式。当前 Order 双副本运行配置要求副本确认；Trade 配置允许副本失败时本地降级提交，两者不能混称为“同步双副本 RPO=0”。先对齐成功响应的提交安全性与切主证明；若要求单节点故障后仍持续交易，需设计并验证满足目标的副本/多数派方案，不能绕过 ACK 或 READY 门禁。
- 把 Order/Trade 副本部署到独立故障域；为 ZooKeeper、数据库、入口和存储消除与同机 A/B 一样的单点。Colima 只用于本地验证，不用于证明跨主机 HA。
- 建立可观测、可重复的故障检测与受控 promotion：epoch fencing、权威 committed prefix、快照安装、Replica 追平、路由刷新、回切。无法证明安全时 fail-closed，禁止双主。
- 验证扩容/缩容及在线分区迁移：增加节点、限速复制、drain、切换、均衡与回滚；迁移期间 API 客户端能处理暂不可用、超时与重连，不丢已确认订单。
- 运行有界混合负载与长稳测试，覆盖 Broker、Trade Robot、Web、下撤单、撮合、资金/风控、行情和投影；注入进程退出、宿主机/磁盘故障、网络隔离、复制延迟、ZooKeeper/DB 不可用、滚动升级与恢复。
- 同时量测入场、撮合完成、复制提交、投影可查四个阶段的持续 TPS 与 p50/p95/p99、积压、拒单、重启/OOM；以订单/成交/资金一致性为硬门槛。先做短时受控诊断，再做 24 小时观察和 72 小时候选长稳（时长为待确认的计划门槛，不是既有成绩）。

**完成证据：** 每种故障的时间线、实测 RTO/RPO、分区与客户端恢复记录、账务/订单不变量、持续容量曲线和安全回滚记录。历史压力数字不得充当当前版本的集群吞吐结论。

## 6. 工作流 D：租户管理，然后平台管理

基础授权先行，产品功能完善按以下顺序：

1. **租户隔离门槛：** 完成 ManagerSvr/AdminSvr 近期改动的全量测试、真实表结构盘点、版本化迁移、同名用户双租户回归和浏览器/API/Topic 攻击矩阵；按 `location + user_id` 发送系统消息，`user_id='*'` 只广播到指定 `location`。旧 `location=NULL` 消息在归属确认前不向任一租户暴露。
2. **租户管理产品：** 用户与子角色、API Key/Robot、品种、费率、风控参数、配额、品牌/域名、审计与导出；停用/到期即时影响会话、交易、Broker 和 Robot 权限，历史数据保留。
3. **平台管理产品：** 申请/审批/暂停/恢复、套餐与配额、跨租户容量和健康视图、告警、发布/回滚、用量计量、操作审批和不可篡改审计。平台管理员必须显式选择目标租户；跨租户统计不得复用普通租户查询绕过隔离。
4. **运营验收：** Tenant Web 与 Platform Web 的实际浏览器操作、角色矩阵、双租户正反向用例、关键配置回滚和审计记录均通过；未实现的按钮保持禁用，不展示虚假的可用功能。

**完成证据：** 全新安装与存量升级两条迁移路径、自动化权限矩阵、浏览器 E2E、审计样本、回滚演练。只完成管理页面不算隔离完成。

## 7. 真实资金上线的独立禁入门槛

以下是并行建设、最终必须同时通过的门槛，不应因为 API 或集群工作完成而跳过：不可变复式账本与连续对账；多源指数/标记价及断流保护；钱包/托管、充值提现审批与外部回执；密钥管理、账户安全和渗透测试；按运营司法辖区确定的合规要求；异地备份、实际恢复演练和故障域隔离。未通过时系统定位为模拟/内部验收环境，不承接真实客户资金。

## 8. 最近一轮执行顺序与发布规则

本节原业务验收顺序保留作后续门槛；近期按上述可复用集群底座计划 F0→F4 推进，Order、Trade、MD 一起纳入。管理面与完整业务专项后排，故障/压测中的订单、资金和行情不变量仍是硬门禁。

1. **现在：** 保持当前运行的交易服务，不做全栈重装；只读完成事故后分区、投影、数据库和数据盘健康核对，留下基线证据。这一步只证明运行/恢复条件，不替代业务计算验收。
2. **随后：** 清理并隔离旧测试活动单；在干净账户逐项验算撮合、费用、盈亏、保证金、资金费、强平、余额/持仓和恢复前后结果，再运行有界端到端验收，不提前启动大压力。
3. **代码并行准备：** 审核并合入 AdminSvr/ManagerSvr 租户修复与系统消息迁移；先在隔离环境做存量升级、API/Topic 和双租户 E2E，再使用不可变镜像晋级。
4. **接口与集群：** 补齐两个外部样板客户端及契约门禁；按业务选定 RTO/RPO 后设计跨宿主机部署、自动切换和在线扩容。
5. **容量与长稳：** 前述正确性门禁通过后恢复阶段性压测；每轮保存镜像 digest、拓扑、数据基线、TPS/延迟、账务一致性和回滚点。
6. **管理面：** 租户管理先验收，再推进平台管理；真实资金禁入门槛单独评审，不随功能验收自动放行。

任何迁移、发布或压测都应在明确环境、目标租户、数据清理方式和回滚点后执行。文档计划本身不代表已经部署、合并、压测或通过生产验收。
