# 现金纯计算与提交/安装闭环：隔离候选验收

日期：2026-09-29。Trade 本地提交 `64acf8e1465f2f68d7182bb8489a8990e6904820`，承接 `40ae10c` 的原结果持久索引/恢复切片。本轮将候选串到真实 Trade 提交协调器，但**未接入线上现金入口**，未退出旧 SQL 写入，也不是集群异常切换或 TPS 验收。

## 已完成的候选闭环

新增纯计算器与显式执行器，均无自动 Spring component。请求和已有账户基线先复制冻结；没有可信账户即拒绝，不自动建账户/伪造零余额。金额先受界限检查，再计算；保留既有可用余额公式及出金时的未实现亏损限制，盈利不增加可提现金额，保证金、冻结字段、账户模式/状态不随现金操作改动。完整账户/租户/风控准入仍须由真实入口实现，测试回调不等于生产认证。

候选执行顺序：同一分区业务屏障内，授权→原结果查重→新请求准入/纯计算→容量预留→状态日志及副本 ACK→提交标记及副本 ACK→安装并核对余额→安装原结果及推进覆盖坐标→发布→返回首次结果。原结果查重成功时仍重新授权，但不重算 PnL、不读取新交易时间、不追加日志、不安装/发布或再次加减资金。相同 ID 的内容冲突在追加前拒绝。

协调器显式候选入口要求集群、journal、commit、state.required、replication.required、lifecycle 均启用；控制面连接、当前 primary/epoch、READY、干净提交尾和索引覆盖坐标全部满足。提交前验证预留令牌与冻结批次完全一致；ACK 需覆盖 seq 并匹配 partition/epoch；阶段之间重新检查权威。旧 `record` 拒绝新 v2，防止绕过安装路径。安装后重新读取账户，必须等于日志中的完整余额后态。

## 不确定提交的处理

- 容量按节点计算，已提交记录及所有分区预留共同占用条数/序列化字节，不淘汰旧请求身份。
- 从尝试追加开始，追加、ACK、安装的运行异常或严重错误都封住分区并撤销 READY。响应前发布失败同样封住分区；不撤销已提交资金。
- 提交/安装不确定时，预留容量保留到可信恢复成功；不能在异常退出时释放给另一分区。恢复 callback 失败也不能释放它。正在执行的预留阻止同分区恢复，其他分区预留参与容量检查。
- 恢复从快照＋已提交 journal 安装资金和原结果。重试返回首次结果，不再次计算；脏尾继续拒绝，不截断历史、不强制切主来通过测试。
- 候选成功安装推进精确覆盖坐标，能生成现金 v3 快照；不确定提交不能捕获快照并覆盖上一份正确文件。

## 尚不能上线的门禁

1. 现金 API 仍没有正式操作 ID、已认证租户/用户绑定及老客户端兼容契约。`State` 回调不是线上完整准入实现；旧 handler/facade/recorder 未接入，`wdBalance` 仍 SQL 先写/先发布。
2. Projection/所有消费者必须先显式升级并验证 v2 完整原结果协议。当前消费者拒绝新格式，不能先启用 writer。
3. 其他旧交易推进 watermark 时还不会推进候选现金索引覆盖证明，因此混合业务会安全拒绝现金，不能直接接入生产。所有事务的覆盖跟踪、全节点恢复/admission 容量、持久冷查询/留存和重试窗口仍需设计验证。
4. 发布不是 durable outbox：崩溃可能遗漏推送，缓存重试不重新发布。Projection GAP 补齐、业务订阅收敛及重复/遗漏投递语义需独立验收。
5. 本轮继承现有 Chronicle 与复制 ACK 契约；没有进程强杀、TCP 故障、断电持久性、quorum/lease、真实副本接管或跨宿主机演练，不能称 RPO=0、HA 或恢复 RTO。冷启动尚未恢复分区的总容量预检也未通过。
6. 可信历史配置/账务基线、资金对账、funding/保险/ADL、本地冷流水以及 SQL 写入方退场未完成。没有自动从数据库补基线、生成空快照、修剪日志或部署/重启/改 assignment。
